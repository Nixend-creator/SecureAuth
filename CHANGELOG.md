## [1.6.4] — 2026-04-14

### Исправление реальных ошибок компиляции

Первая настоящая проверка реальным Gradle-компилятором за весь проект
(среда разработки не имела доступа к services.gradle.org все предыдущие
версии — только ручная сверка сигнатур API). Компилятор нашёл 2 ошибки,
обе — следствие правок из более ранних раундов работы, которые невозможно
было поймать без реальной компиляции.

**Ошибка 1 — `TotpService.java:187: cannot find symbol backupCodes`.**
При добавлении защиты от TOTP-replay (1.4.16) объявление переменной
`List<String> backupCodes = generateBackupCodes(...)` было случайно
"съедено" операцией текстовой замены вместе со строкой, которую нужно
было заменить, и не восстановлено. Исправлено — объявление возвращено на
место в `confirmSetup()`.

**Ошибка 2 — `AdminCommand.java:277: incompatible types List<CAP#1> cannot
be converted to List<Player>`.** В `/saadmin 2fa-status` (1.6.2)
`getOnlinePlayers()` возвращает `Collection<? extends Player>` —
`.stream().filter(...).toList()` от такой коллекции даёт `List<CAP#1>`
(захваченный wildcard-тип), который нельзя напрямую присвоить
`List<Player>`. Исправлено — тип переменной изменён на
`List<? extends Player>` (список только читается, не модифицируется,
поэтому wildcard подходит без потери функциональности).

**После обеих находок** — вручную перечитаны целиком `TotpService.java` и
`AuthCommand.java` (самый часто редактируемый файл за весь проект,
739 строк) на предмет других похожих "потерянных" объявлений — других
экземпляров не найдено.

## [1.6.2] — 2026-04-12

### Шаг 4 рекомендаций после аудита — /saadmin 2fa-status

**Новое:** `/saadmin 2fa-status` — показывает, у кого из ОНЛАЙН игроков с
правом `two-factor.require-for-permission` включена 2FA, а у кого нет.
Раньше единственным способом узнать это было проверять каждого игрока
вручную; теперь один отчёт сразу показывает всех, кто ещё не настроил
обязательную защиту.

**Почему только онлайн-игроки:** надёжная проверка прав у ОФФЛАЙН игрока
требует API плагина разрешений (LuckPerms/Vault) — а мы только что
намеренно убрали неиспользуемую интеграцию с ними как мёртвый код
(1.5.0). Тянуть эту зависимость обратно ради одного отчёта не оправдано.
Список онлайн-игроков и так самый практически полезный — это те, кого
можно сразу же и лично попросить включить 2FA.

**Добавлена** permission-нода `secureauth.admin.2fa-status` — по тому же
паттерну, что и у остальных подкоманд `/saadmin` (auto-grant через
родителя `secureauth.admin` плюс отдельная гранулярная нода для точечной
выдачи прав модераторам).

## [1.6.1] — 2026-04-11

### Шаг 3 рекомендаций после аудита — команда самообслуживания /session

**Новое:** `/session` — показывает статус доверенной сессии на аккаунте:
IP, дату создания, дату истечения. Позволяет игроку самому заметить
незнакомый IP на своём аккаунте, не дожидаясь администратора. Требует уже
быть авторизованным (тот же принцип, что и у `/setemail`).

**Новое:** `/session revoke` — отзывает доверенную сессию БЕЗ выхода из
текущего подключения, в отличие от `/logout`. Разный юзкейс: "перестать
доверять текущему устройству/IP на будущее" — не то же самое что "выйти
из игры прямо сейчас".

**Реализация:** добавлен `SessionRepository.findSessionInfo()` (в отличие
от уже существующего `findValidSessionIp()`, возвращает сессию даже если
она уже истекла — чтобы показать "последняя сессия истекла тогда-то", а
не просто "сессии нет"). `SessionService.getSessionInfo()` — тонкая
обёртка с логированием ошибок, не бросающая исключений наружу.

## [1.6.0] — 2026-04-10

### Шаг 2 рекомендаций после аудита — асинхронный рефакторинг onPlayerJoin

Самый рискованный пункт из списка рекомендаций. Эта функция ловила баги
5+ релизов подряд на протяжении всего проекта (сессии, IP, слепота), и
именно поэтому раньше сознательно не трогалась при находке синхронных
DB-вызовов на главном потоке во время аудита.

**Что было:** проверка бана по IP, GeoIP и валидности сессии выполнялись
СИНХРОННО на главном потоке прямо внутри `onPlayerJoin` — три блокирующих
вызова (промах кэша антибота, файловый lookup MaxMind, JDBC round-trip
для проверки сессии) внутри обработчика Bukkit-события. Прямое нарушение
собственного правила проекта "DB-вызовы всегда асинхронно", которое
последовательно применялось везде кроме этого единственного места.

**Почему это было безопасно откладывать асинхронно:** реальная граница
безопасности здесь — не слепота (чисто визуальный эффект), а проверка
`AuthState.isAuthenticated()` внутри `ProtectionListener`. `AuthState`
по умолчанию создаётся в состоянии PENDING — игрок уже полностью
ограничен (не может двигаться, писать в чат, выполнять команды) с
момента входа, независимо от того, применена ли слепота и принято ли
решение о бане/сессии. Значит вынести это решение на виртуальный поток
можно без реального разрыва в защите — в худшем случае решение появится
на несколько миллисекунд позже, а не сразу же в том же тике.

**Реализовано:** проверки бана, GeoIP и сессии перенесены в виртуальный
поток; результат передаётся обратно на главный поток через
`mainThreadExecutor` для непосредственно всех действий (кик, снятие
слепоты, применение слепоты, показ сообщений, планирование таймаута).
Добавлена защита `player.isOnline()` перед выполнением любого действия —
игрок мог отключиться (или отключиться и мгновенно переподключиться,
получив новый `AuthState`) за то короткое время, пока шла проверка.

**Компромисс, о котором стоит знать:** сторонний плагин, читающий
`AuthApi.isAuthenticated()` синхронно из СВОЕГО обработчика
`PlayerJoinEvent` (на любом приоритете), теперь может увидеть "ещё не
аутентифицирован" для сессии, которая будет восстановлена через мгновение.
До этого изменения решение уже было финальным к моменту завершения
обработки `PlayerJoinEvent`; теперь оно появляется чуть позже. Учитывая,
что альтернативой было блокирование главного потока сервера при каждом
входе, это признано оправданным компромиссом — но это реальное изменение
поведения для любой интеграции, полагающейся на синхронную доступность
во время `PlayerJoinEvent`.

**Не изменилось:** конструктор `AuthListener` (все зависимости те же),
внешнее поведение для игрока (сообщения, тайминг кика по таймауту —
теперь отсчитывается от момента получения решения, а не от исходного
входа, разница практически неощутима), сигнатуры `SessionService`/
`AntiBotService`/`GeoIpService`.

## [1.4.23] — 2026-04-08

### Продолжение аудита — рассинхрон времени в /saadmin stats

Систематически проверял другие категории db-специфичного SQL после двух
находок с upsert-синтаксисом. `LIMIT`, `RETURNING`, конкатенация строк —
чисто. Но нашёл смежную проблему на стыке двух уже известных механизмов.

#### 🟡 СРЕДНЕ — счётчик активных банов в /saadmin stats мог врать
`IpBanRepository.isBanned()` (реальная проверка бана) сравнивает
`expires_at` с `LocalDateTime.now()` — временем JVM. А `getStats()` для
ТОГО ЖЕ САМОГО поля использовал `NOW()`/`datetime('now')` — время
СЕРВЕРА БАЗЫ ДАННЫХ. Особенно заметно на SQLite: `datetime('now')` в
SQLite по документации возвращает UTC, а не локальное время — если
таймзона JVM отличается от UTC (типичная ситуация для серверов не в
UTC-поясе), счётчик "активных банов" в статистике администратора мог
показывать неверные цифры, хотя реальная блокировка IP всё это время
работала корректно (баг чисто отображения/отчётности, не безопасности).

**Исправлено:** запрос `activeBans` теперь использует тот же источник
времени, что и настоящая проверка в `IpBanRepository.isBanned()` —
Java-вычисленное время, а не серверное. Добавлена параметризованная
перегрузка `queryInt()` вместо встраивания значения прямо в SQL-строку.

**Проверено — `activeSessions` фикса не требует:** сессии, в отличие от
IP-банов, изначально (с самых первых версий этого проекта) были переведены
на серверное время БД именно в `SessionRepository` — там `NOW()`/
`datetime('now')` в `getStats()` уже согласован с реальной проверкой.

## [1.4.22] — 2026-04-07

### КРИТИЧНО — включение 2FA тоже было полностью нерабочим на MySQL

Прямое продолжение вчерашней находки: раз баг с непортированным
upsert-синтаксисом нашёлся в одном файле, систематически прогрепал ВСЮ
кодовую базу на тот же класс проблемы — `ON CONFLICT`, `ON DUPLICATE KEY`,
`INSERT OR REPLACE`, `REPLACE INTO`.

**Найден второй экземпляр:** `TotpRepository.save()` — метод, вызываемый
при подтверждении `/2fa enable <код>` — использовал ту же SQLite-only
конструкцию `ON CONFLICT(uuid) DO UPDATE SET ... excluded.column` без
ветвления по типу БД. **Практический эффект:** любая попытка включить
двухфакторную аутентификацию на MySQL/MariaDB сервере бросала бы
`SQLSyntaxErrorException` — вся функция 2FA была недоступна в продакшене
на MySQL, хотя прекрасно работала на SQLite (что объясняет, почему это
не всплыло раньше — тестирование велось на SQLite).

**Исправлено** — тем же паттерном что и вчера: MySQL получает
`ON DUPLICATE KEY UPDATE ... VALUES(column)`, SQLite — прежний рабочий
синтаксис.

**Проверено, других экземпляров не найдено:** прогрепана вся кодовая база
на `INSERT OR REPLACE`, `INSERT OR IGNORE`, `REPLACE INTO` — пусто.
`PlayerRepository` не использует upsert вообще (только чистые
`insert`/`update`, конфликт-резолюция не требуется по дизайну).

## [1.4.21] — 2026-04-06

### КРИТИЧНО — бан по IP был полностью нерабочим на MySQL/MariaDB

Впервые за весь аудит открыл `IpBanRepository.java` целиком — файл,
который упоминался десятки раз, но никогда не читался полностью.

**Причина:** `ban()` использовал SQLite-специфичный upsert-синтаксис
(`ON CONFLICT(ip_address) DO UPDATE SET ... excluded.column`) БЕЗ ветвления
по типу БД — единственный репозиторий во всём проекте, который так делает
(`SessionRepository`, `RecoveryTokenRepository`, `EmailChangeRepository` —
все корректно проверяют `db.isMysql()` именно из-за того, что
upsert-синтаксис — один из самых несовместимых между СУБД элементов SQL).
MySQL/MariaDB вообще не понимает `ON CONFLICT`/`excluded.` — это чисто
SQLite-синтаксис. Любой вызов `ban()` на MySQL/MariaDB бросал бы
`SQLSyntaxErrorException`.

**Практический эффект:** вся система бана по IP была полностью нерабочей
на любом продакшн-сервере с MySQL/MariaDB — и внутренняя логика AntiBot
(автобан после флуда/подбора паролей), и публичный `AntiBotApi.banIp()`
для сторонних плагинов. При этом `isBanned()`/`unban()`/`deleteExpired()`
работали нормально на обеих БД (обычные SELECT/DELETE — совместимый ANSI
SQL), поэтому проблема проявлялась только в момент попытки ЗАБАНИТЬ,
что легко было принять за "антибот просто не сработал" вместо явной
ошибки в логах.

**Исправлено:** `ban()` теперь ветвится по `db.isMysql()` — MySQL получает
`ON DUPLICATE KEY UPDATE ... VALUES(column)`, SQLite — прежний
`ON CONFLICT ... excluded.column`.

**Также проверено:** `LocalDateTime.now()` в этом файле (вместо DB-side
`NOW()`, как в остальных репозиториях) — не баг: и запись, и чтение
используют время ОДНОЙ и той же JVM, без сравнения с серверным временем
БД, поэтому таймзона-рассинхрон (класс бага, найденный и исправленный для
сессий в самом начале этого аудита) здесь структурно невозможен.

## [1.4.20] — 2026-04-05

### Продолжение аудита — самокритика вчерашнего фикса

Проверил прямое следствие фикса из 1.4.19: не создаёт ли новая
персистентная блокировка сама по себе проблему для легитимных
пользователей.

#### 🟠 ВЫСОКАЯ ВАЖНОСТЬ — восстановление пароля не снимало блокировку
Игрок, заблокированный по `max-login-attempts` (персистентная проверка из
1.4.19), успешно восстанавливал пароль через `/recover confirm` или
`/changepassword` — и немедленно блокировался СНОВА при первом же входе с
ПРАВИЛЬНЫМ новым паролем, поскольку `countRecentFailures()` считал старые
записи `LOGIN_FAIL` в `sa_audit_log`, а смена пароля их никак не
затрагивала. Ирония ситуации: механизм восстановления существует именно
для того чтобы вернуть доступ заблокированному пользователю, а мой же
вчерашний фикс это восстановление тут же обесценивал.

**Исправлено без изменения схемы БД** — переиспользованы уже логируемые
события `PASSWORD_CHANGE` и `PASSWORD_RESET` (оба уже писались в
`sa_audit_log` при `/changepassword` и `/recover confirm` соответственно).
`countRecentFailures()` теперь считает только `LOGIN_FAIL`, произошедшие
ПОСЛЕ последней смены/сброса пароля на аккаунте — смена пароля стандартно
и ожидаемо снимает блокировку, как и должно быть в любой системе учёта
неудачных попыток.

## [1.4.19] — 2026-04-04

### КРИТИЧНО — лимит попыток входа сбрасывался переподключением

Самая серьёзная находка со времён `/recover` в 1.4.1.

**Причина:** `AuthState` (в т.ч. счётчик неудачных попыток) создаётся
ЗАНОВО при каждом новом подключении (`authStates.put(uuid, new
AuthState())`). Значит `security.max-login-attempts` (по умолчанию 5) и
`ban-duration-minutes` (30 минут блокировки) работали только В ПРЕДЕЛАХ
ОДНОГО соединения. Скрипт атакующего мог: исчерпать лимит попыток →
переподключиться → получить свежий `AuthState` со счётчиком 0 → повторять
бесконечно. Единственной реальной защитой оставался слабый
`rate-limit.login-max` (10 попыток/60 секунд, не привязан к `AuthState`,
переподключением не сбрасывается) — но это ~1 попытка в 6 секунд БЕЗ
ограничения по времени, а не строгая эскалирующая блокировка, которую
задумывал `max-login-attempts`.

Также обнаружена связанная деталь: в БД годами существовала отдельная
таблица `sa_login_attempts` с методами `PlayerRepository.recordAttempt()`
и `countFailedAttemptsSince()`, явно спроектированными для этой самой
персистентной защиты — но нигде не вызываемыми (мёртвый код).

**Исправлено:** вместо оживления отдельной неиспользуемой таблицы,
переиспользован уже надёжно работающий `sa_audit_log` (туда каждый
неудачный вход и так пишется через `AuditEvent.LOGIN_FAIL`). Добавлен
`AuditLogService.countRecentFailures(uuid, minutes)` — считает
неудачные входы за окно `ban-duration-minutes`. Проверка встроена в
`/login` ПЕРЕД запуском дорогой Argon2-проверки: если персистентный
счётчик неудач уже достиг `max-login-attempts` — игрок сразу кикается,
без траты ресурсов на хеширование заведомо отклонённого пароля.

**Проверено — 2FA-путь фикса не требует:** `/2fa <код>` защищён отдельным
`totp-max: 5` попыток / 60 секунд против 6-значного кода (1 000 000
комбинаций) — уже само по себе делает подбор практически невозможным
независимо от сброса `AuthState`. Счётчик `incrementFailures()` там нужен
только для косметического сообщения "осталось попыток", не является
реальной границей безопасности.

### Продолжение аудита — гонка между регенерацией и проверкой backup-кодов

Естественное продолжение вчерашней находки: у `verifyBackupCode()` теперь
есть блокировка на аккаунт, но `regenerateBackupCodes()` её не разделяла.

#### 🟡 СРЕДНЕ — обычный пользовательский сценарий мог "воскресить" старые коды
Реалистичный, не требующий атакующего сценарий: игрок использует

БЕЗ той же блокировки, что и проверка. Если "устаревшая" запись от

новые коды (только что увиденные на экране), а реальные валидные коды в
БД — старые, которых у него уже нет под рукой. Риск реального
блокирования легитимного пользователя от возможности восстановления
через backup-коды.

**Исправлено:** `regenerateBackupCodes()` теперь берёт ту же самую
блокировку на аккаунт, что и `verifyBackupCode()` — операции стали
взаимоисключающими для одного и того же игрока.

**Проверено, находок нет:** `confirmSetup()` (первичная настройка 2FA) и
`repo.disable()` (отключение) не пересекаются с этой гонкой — первая
выполняется до того как 2FA включена вообще (проверка backup-кода
невозможна), вторая пишет в отдельную колонку `enabled`, не трогая
`backup_codes`.

## [1.4.17] — 2026-04-02

### Продолжение аудита — гонка на backup-кодах 2FA

Естественное продолжение находки про TOTP replay (1.4.16) — проверил тот
же класс проблем на backup-кодах.

#### 🟡 СРЕДНЕ — backup-код мог сработать дважды при гонке
`verifyBackupCode()` делал классический read-modify-write без
синхронизации: читал список кодов (снимок из памяти), проверял совпадение,
затем перезаписывал весь список с пометкой "USED:". Два запроса,
пришедшие в очень быстрой последовательности (например, при
дублирующей отправке одной и той же команды модифицированным клиентом),
могли оба прочитать код как неиспользованный ДО того как любой из них
успевал записать пометку — оба вернули бы `true`, хотя backup-код по
своей природе обязан быть строго одноразовым. Окно гонки узкое (в отличие
от /login там нет медленного Argon2-хеширования — только быстрый SQL), но
реальное.

**Исправлено:** проверка и запись теперь сериализованы через lock на
аккаунт, при этом внутри блокировки данные перечитываются заново из БД
(а не берутся из "устаревшего" снимка, полученного до захвата блокировки)
— иначе одной синхронизации записи было бы недостаточно, второй поток всё
равно принял бы решение по старым данным. Карта блокировок намеренно НЕ
на TTL-кэше (в отличие от `lastUsedBucket` из прошлой находки) — эвикция
объекта блокировки прямо во время использования могла бы разбить саму
синхронизацию на два разных объекта. Рост ограничен количеством
уникальных аккаунтов, когда-либо использовавших backup-код за всё время
работы сервера — не произвольными подключениями ботов, поэтому
неограниченная карта здесь безопасна.

## [1.4.16] — 2026-04-01

### Продолжение аудита — защита TOTP от replay-атаки

#### 🟡 СРЕДНЕ — TOTP-код можно было использовать повторно в течение окна
`isValidTotp()` проверял текущий time-bucket ±1 (окно ~90 секунд), но
никак не отмечал уже использованный код как "потраченный" — один и тот же
6-значный код оставался валидным для ЛЮБОГО количества входов в течение
всего окна. Это классический пробел, который эксплуатируют
real-time-фишинг-релеи 2FA (поддельная страница логина мгновенно
ретранслирует введённый жертвой код на настоящий сервер) и банальный
шпионаж через плечо/запись экрана — на серьёзном отличии от пароля: пароль

работать МАКСИМУМ один раз. Требует чтобы первый фактор (пароль) тоже был
скомпрометирован, поэтому это узкий, но реальный пробел в defense-in-depth.

**Исправлено:** добавлено отслеживание последнего успешно использованного
time-bucket на аккаунт (`Cache<UUID, Long>`, TTL 5 минут — с запасом
покрывает 90-секундное окно, самоочищается для неактивных аккаунтов). Код
для bucket'а меньше или равного последнему использованному теперь
отклоняется — стандартная практика для любой серьёзной TOTP-реализации.
Применяется во всех трёх местах верификации: `/2fa enable` (подтверждение
настройки), `/2fa <код>` (обычный вход), `/2fa disable`.

## [1.4.15] — 2026-03-31

### Продолжение аудита — атомарность миграций БД

Проверил `MigrationManager` целиком (в духе находки про атомарность reload
конфига из 1.4.13) — что происходит, если миграция упадёт на середине.

#### ✅ Проверено, находок нет — но с важной оговоркой на будущее
Механизм уже использует явную транзакцию с `rollback()` при ошибке — но
важный нюанс: в MySQL/MariaDB DDL-операции (`CREATE TABLE` и т.д.) всегда
делают неявный commit ДО выполнения, независимо от `setAutoCommit(false)`
— это ограничение InnoDB, а не баг данного кода. Значит при сбое на
середине скрипта уже выполненные `CREATE TABLE` реально закоммичены и
"rollback" их не отменяет. Проверил все 5 текущих миграций (MySQL и
SQLite) — везде используется `CREATE TABLE IF NOT EXISTS` / `TRUNCATE` /
`DELETE FROM` (все идемпотентны), поэтому повторный запуск с нуля при
следующем старте сервера безопасен: уже созданные таблицы просто
пропускаются.

**Добавлено:** подробный комментарий прямо в `runIfNeeded()`, объясняющий
это ограничение и требующий от будущих миграций той же идемпотентности
(`IF NOT EXISTS`, `ON DUPLICATE KEY UPDATE` вместо голого `INSERT` и т.д.)
— иначе неидемпотентная миграция (например, `ALTER TABLE ADD COLUMN` без
проверки) после единственного частичного сбоя навсегда сломает запуск
плагина при каждой последующей попытке.

## [1.4.11] — 2026-03-27

### КРИТИЧНО — MiniMessage-инъекция через плейсхолдеры сообщений

Самая серьёзная находка за весь аудит после `/recover`.

**Причина:** `LanguageManager.build()`/`buildKick()` подставляли значения
плейсхолдеров (`{email}`, `{player}`, `{reason}` и т.д.) как сырую строку
ПРЯМО в шаблон ДО парсинга MiniMessage — комментарий в коде даже прямо
признавал это. Значение email из `/setemail` проверялось только регулярным
выражением "есть @ и точка" — оно пропускает `<`, `>`, `:`, `'`. Значит
можно было создать email вида:

```
attacker@evil<click:run_command:'/op attacker'>.com
```

Такая строка, попав в шаблон сообщения и будучи задеserialize'ена как
MiniMessage, превращалась в НАСТОЯЩИЙ кликабельный тег. Если подобное
значение когда-либо отобразится на экране администратора (например, через
будущий admin-просмотр привязанных email), замаскированный клик мог
выполнить произвольную команду от имени админа — классический stored-XSS,
только для игрового чата вместо браузера.

**Исправлено:** каждое значение плейсхолдера теперь проходит через
`MiniMessage.escapeTags()` — официальный API Adventure именно для
недоверенного ввода ("Useful for untrusted input", как написано в их же
javadoc) — ПЕРЕД подстановкой в шаблон. Любая MiniMessage-разметка внутри
значения теперь отображается как безобидный литеральный текст, а не
интерпретируется как настоящий тег. Синтаксис `{key}` в lang-файлах не
менялся — заменять на угловые скобки (`<key>`, родной синтаксис тегов
MiniMessage) не потребовалось.

**Также проверено:** email-письма (`EmailService`) интерполируют `username`
без экранирования HTML, но это `player.getName()`, ограниченный алфавитом
Mojang — риск инъекции там практически отсутствует на online-mode серверах.
Оставлено без изменений как минорное замечание.

## [1.3.9] — 2026-03-15

### Bug fix — Сессия не восстанавливалась на dual-stack серверах (IPv4 vs IPv6)

**Причина:** на хостинге с dual-stack (IPv4+IPv6) Paper может

На локальном сервере формат не менялся и сессия работала.

IPv4-mapped IPv6 (`::ffff:x.x.x.x`) автоматически разворачивается
в чистый IPv4. Нормализация применяется в `onPlayerLogin`
и `onAsyncPreLogin` — единый источник IP для всех последующих
операций (state.loginIp → запись сессии → проверка).

**Обновление с 1.3.8:** только JAR, миграций нет.
Старые сессии в `sa_sessions` будут очищены
автоматически (ShutdownManager.cleanExpired), игрокам

- `AuthListener.onPlayerLogin` — записывает `state.setLoginIp(event.getRealAddress())` — единственный источник IP
- `AuthCommand.completeAuth` — берёт IP из `state.getLoginIp()` вместо `player.getAddress()`

## [1.3.3] — 2026-03-09

### Bug fix — Сессия не сохранялась на MySQL/MariaDB (боевой сервер)

**Причина 1 — Главная: `sessions.create()` блокировал main thread и глотал исключения**
- Запись сессии вызывалась синхронно в 4 местах (включая `completeAuth`, `onPlayerLogin`) — на боевом сервере MySQL через сеть даёт 10–50ms на запрос
- Если в этот момент пул соединений был занят асинх операциями — `getConnection()` блокировался до timeout или бросал `DatabaseException`
- `DatabaseException` нигде не перехватывался: Paper ловил его в консоль, игрок входил но сессия **не записывалась**
- Исправлено: `SessionService.create()` / `invalidate()` теперь выполняется через Virtual Thread; `DatabaseException` перехватывается и логируется как WARN, не прерывая аутентификацию

**Причина 2 — Старые строки в `sa_sessions` с неверным `expires_at`**
- До v1.3.2 `expires_at` записывался в локальной таймзоне JVM. На боевом сервере все старые строки содержат неверное время
- Добавлена миграция V3 (`TRUNCATE TABLE sa_sessions`): при первом старте автоматически очищает все старые сессии

**Обновление с 1.3.2**: только JAR. При старте все сессии будут автоматически сброшены (V3 миграция) — игрокам потребуется войти один раз вручную.

## [1.3.2] — 2026-03-05

### Bug fix

**Сессии не сохранялись — игрокам приходилось вводить пароль при каждом заходе**

Корневых причин было две:

1. **`DatabaseManager` — отсутствие `serverTimezone=UTC` в JDBC URL**
   - MySQL/MariaDB коннектор без явного `serverTimezone` использует системную таймзону JVM
   - Если таймзона JVM отличалась от таймзоны БД — `expires_at > NOW()` всегда возвращало `false`, сессия считалась истёкшей сразу после создания
   - Исправлено: добавлен `&serverTimezone=UTC` в JDBC URL

2. **`SessionRepository` — даты сравнивались как строки через `setString()`**
   - `expires_at` записывался через `LocalDateTime.format()` + `setString()` — Java отдавала время в локальной таймзоне JVM, а база хранила в своей
   - Переписан: `expires_at` теперь вычисляется целиком на стороне БД (`DATE_ADD(NOW(), INTERVAL ? MINUTE)` / `datetime('now', '+N minutes')`); проверка тоже через `NOW()` на стороне БД — никакой конверсии времени Java больше нет

**`AuditEvent` — добавлен `DISCONNECT`**
- `onPlayerQuit()` записывал `LOGOUT` вместо `DISCONNECT`; исправлено

**Обновление с 1.3.1**: только JAR. Структура БД не менялась — пересоздавать таблицы не нужно.

### Технические заметки

**Почему не Flyway?**
Flyway 11.13+ крашится в fat jar с `Unknown prefix for location: classpath:db/callback`
(flyway/flyway#4157). Downgrade до 11.12.0 избегал этого, но не поддерживал SQLite 3.49+.
Собственный `MigrationManager` — 150 строк, нулевые зависимости, полностью надёжен.

**Paperweight + Shadow**
`paperweight-userdev` 2.0.0-beta.19 автоматически обнаруживает Shadow и прокидывает
`reobfJar → shadowJar`. Ручная установка `inputJar` не нужна и ломает сборку.
Shadow 9.3.1 обязателен для поддержки Java 21 лямбд (ASM invokedynamic).

**config-version: 2**
Версия конфига повышена в 1.0.0 (добавлен раздел `webhooks:`).
При обновлении с rc.11: удалите `config.yml` или добавьте секцию вручную.
